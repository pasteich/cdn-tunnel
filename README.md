# CDN Tunnel

Туннель TCP/UDP-трафика через CDN одним Go-файлом + Android-обёртка (VPN).

Клиент поднимает локальный **SOCKS5**; трафик идёт через CDN (TLS+HTTP/2, SNI),
реальные исходящие коннекты делает сервер (исходящий IP = IP сервера).
Вниз — длинный потоковый ответ, вверх — chunked-запросы (или потоковый `stream`).

## Сборка
```bash
go build -o tunnel .
```

## Сервер (origin, за CDN)
```bash
./tunnel -server -addr :80 -password 123456 -method both -users 3
```
`-users N` — сколько клиентов сервер обслуживает одновременно (0 = без лимита).
Слот занимает клиент целиком (пул `-conns` и все его стримы — один пользователь),
клиенту сверх лимита сервер отвечает **429** и пишет в журнал:
```
⚠ отказ: достигнуто максимальное число подключений 3/3 — клиент a1b2c3d4 (1.2.3.4) отклонён
```
Слот освобождается, когда клиент присылает `/bye` (по Ctrl-C / SIGTERM) или
молчит дольше 45 секунд (клиент пингует сервер каждые 15 с). Отклонённый клиент
печатает `STATUS userlimit` и сообщение о лимите.

## Клиент (локальный SOCKS5)
```bash
./tunnel -client -ip <CDN_IP> -host <cdn.domain> -password 123456 \
         -listen 127.0.0.1:8090 -name "dmitry"
# затем: curl --socks5-hostname 127.0.0.1:8090 https://api.ipify.org
```
`-name` — под этим именем клиент виден в списке пользователей сервера
(без него — «гость-<id>»). Имя же служит ключом слота: один человек, сколько бы
раз он ни перезапускался, занимает один слот из `-users`.

## Ссылка cdn:// (поделиться настройками)
```bash
# собрать ссылку из текущих параметров:
./tunnel -share -ip <CDN_IP> -host <cdn.domain> -password 123456
cdn://AYutF0ZIlOWh-DylEfgZumfC3J3i5MEhm05TYXNIC_bN…  (пример)

# подключиться по ссылке (перекрывает -ip/-host/-password/-conns/-method/-transport):
./tunnel -client -link "cdn://AYutF0…" -name "dmitry"
```
В ссылке **нет мастер-пароля**: она несёт собственное удостоверение
`<id>.<подпись>` (HMAC-SHA256 от `-password` сервера). Сервер проверяет подпись,
ничего не зная о ссылке заранее, и **привязывает её к первому устройству**,
которое по ней подключилось (`-device`, по умолчанию хеш `/etc/machine-id`).
Второму устройству с той же ссылкой — `409` и «ссылка уже использована»:

```bash
./tunnel -client -link "cdn://…"      # первое устройство: работает
./tunnel -client -link "cdn://…"      # другое устройство: ✗ ссылка уже использована
```
Снять привязку: `/admin/unbind` (см. ниже) или кнопка «Отвязать» в приложении.

Содержимое зашифровано **AES-256-GCM** (ключ = SHA-256 общего секрета, nonce
случайный, версия формата в AAD), поэтому глазами в ссылке ничего не прочитать
и base64-декод ничего не даёт. Ключ одинаков во всех сборках — иначе получатель
не расшифровал бы ссылку, — так что это стойкая обфускация, а не тайна от того,
у кого есть бинарник: доступ решает пароль туннеля внутри ссылки. Тот же формат
понимает Android-приложение (вкладка «Ссылка» и открытие `cdn://…` из мессенджера).

## Кто сейчас на сервере
```bash
curl -H "X-Tunnel-Auth: 123456" https://<cdn.domain>/users
{"limit":2,"online":1,"users":[{"name":"dmitry","online":true,"since":…,"last":…,"seen":3},
                               {"name":"artem","online":false,"last":…,"seen":1}]}
```
Сервер помнит всех, кого видел: подключённые — `online: true`, остальные остаются
в списке как офлайн. Список переживает перезапуск сервиса (файл `-state`,
по умолчанию `/var/lib/cdn-tunnel/users.json`). Клиент опрашивает эту ручку раз
в 5 секунд и печатает строку `ROSTER {json}` при каждом изменении состава —
её читает Android-приложение (вкладка «Юзеры»).

## Админка сервера (`/admin`)
Только с мастер-паролем (`X-Tunnel-Auth`), удостоверением ссылки не открывается.
Приложение ходит в неё по SSH через `curl` на localhost, наружу светить не нужно.

| Ручка | Что делает |
|-------|-----------|
| `GET /admin` | снимок: версия, аптайм, лимит, онлайн, трафик сервера и по каждому клиенту, привязки ссылок |
| `GET /admin/kick?name=X` | согнать клиента с линии (слот освобождается) |
| `GET /admin/ban?name=X` / `unban` | заблокировать / разблокировать (забаненный получает 403 `banned`) |
| `GET /admin/unbind?name=X` \| `?link=ID` \| `?all=1` | снять привязку ссылки к устройству |
| `GET /admin/link/new?label=Андрею` | **выпустить ссылку**: сервер заносит её в реестр и возвращает `{id, cred}` |
| `GET /admin/link/revoke?id=…` / `restore` | отозвать ссылку (клиент получает 403) / вернуть |
| `GET /admin/link/unbind?id=…` | отвязать от устройства, оставив рабочей |
| `GET /admin/link/delete?id=…` | удалить запись вместе со счётчиками |
| `GET /admin/link/rename?id=…&label=…` | сменить подпись |
| `GET /admin/forget?name=X` | убрать клиента из списка вместе со счётчиками |
| `GET /admin/limit?n=3` | сменить `-users` **на ходу**, без перезапуска |

```bash
curl -s -H "X-Tunnel-Auth: мастер" http://127.0.0.1/admin | jq .
curl -s -H "X-Tunnel-Auth: мастер" "http://127.0.0.1/admin/limit?n=5"
```
Трафик считается **по каждому клиенту и по каждой ссылке** (↓/↑ за всё время) и
переживает перезапуск — лежит в файле `-state` вместе со списком клиентов и
реестром ссылок. Реестр ведёт сервер, поэтому владелец видит и ни разу не
использованные ссылки, и может отозвать любую.

Ручка `/users` (её опрашивают клиенты для вкладки «Юзеры») отдаёт только состав —
кто онлайн, кто офлайн. Трафик, адреса и устройства видны исключительно в `/admin`.

## Ключевые флаги
| Флаг | Назначение |
|------|-----------|
| `-password` | общий секрет (заголовок `X-Tunnel-Auth`, сверка в постоянное время; пусто = без пароля) |
| `-method` | клиент: `post`\|`get`; сервер: `post`\|`get`\|`both` (что принимать) |
| `-transport` | `chunked` (любой CDN) \| `stream` (один потоковый POST вверх, ниже пинг; при буферизующем CDN — авто-откат на chunked) |
| `-fastopen` | оптимистичный SOCKS-ответ (−1 RTT на соединение) |
| `-conns` | число TCP/h2-соединений к CDN (пул) |
| `-udp` | UDP ASSOCIATE (DNS/QUIC/прочий UDP) |
| `-window` | окно up-запросов в полёте (chunked) |
| `-idle` | таймаут простоя стрима на сервере, сек |
| `-users` | сервер: максимум одновременных клиентов (0 = без лимита) |
| `-name` | имя клиента в списке пользователей (и ключ его слота) |
| `-state` | сервер: файл со списком известных клиентов (по умолч. `/var/lib/cdn-tunnel/users.json`) |
| `-link` | клиент: подключиться по ссылке `cdn://…` |
| `-cred` | клиент: удостоверение ссылки `<id>.<подпись>` без самой ссылки |
| `-device` | отпечаток устройства для привязки ссылки (по умолчанию сам) |
| `-share` | напечатать ссылку `cdn://…` с текущими настройками и выйти |
| `-stats` | машиночитаемый вывод `STATS ...` (для Android-обёртки) |

## Зачем серверу `-password`, если есть ссылки
`-password` — это **мастер-ключ сервера**, а не «ещё один пароль для друга»:
- им подписываются удостоверения ссылок (`<id>.<подпись>` = HMAC мастер-ключа),
  поэтому сервер проверяет любую ссылку, ничего о ней заранее не зная;
- им открывается админка `/admin*` (удостоверением ссылки — нет);
- по нему владелец может подключиться напрямую, без ссылки и без привязки к устройству.

Друзья мастер-ключ не видят и не вводят: у них только ссылка, привязанная к их
устройству и отзываемая в один тап. Без `-password` ссылки выпускать нечем, а сам
сервер открыт любому, кто знает домен CDN.

## Транспорт и безопасность
- TLS есть только на участке **клиент → CDN**; CDN → origin — обычный HTTP:80.
- Пароль защищает доступ: без верного пароля любой путь, кроме `/`, отдаёт **403**.
- `-users` считает клиентов по имени (`X-Tunnel-Name`), а безымянных — по
  `X-Tunnel-Client` или исходному IP; проверка пароля идёт **перед** учётом,
  поэтому чужак с неверным паролем ни слот не занимает, ни в список не попадает.
- Ссылка `cdn://…` шифрует конфиг, но не заменяет пароль: у кого ссылка — у того
  доступ к серверу, так что делитесь ей так же осторожно, как паролем.
- `stream`/WebSocket-полнодуплекс требует CDN, не буферизующего тело запроса.
